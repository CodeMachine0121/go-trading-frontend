# Product Requirements Document (PRD) — 外掛授權同意頁

**Status:** Finalized
**Version:** v1.0
**Owner:** James Hsueh
**Stakeholders:** 交易服務、外掛（Claude Code 連線器）、操作台

---

## 1. Background & Goal (Why & Goal)

- **Problem Statement:** 今天讓 Claude Code 代使用者操作交易服務，得在對話裡交出電子郵件與密碼：
  密碼留在對話紀錄裡，外掛握著的是能以他身分做任何事的帳密本身，而且登入過期時還得再給一次。
- **Expected Outcome:** 外掛要身分時把使用者送到操作台的**外掛授權同意頁**；使用者在操作台自己的登入畫面登入，
  看清楚是哪一個外掛、要的是什麼，親手按「允許」或「拒絕」，結果交回外掛。
  成功的標準：**使用者從此不必把密碼交給任何外掛**；每一次授權都是他本人在這一頁親手按下的；
  每一種結局（允許、拒絕、請求已失效、連不上）都告訴他下一步去哪。
- **Out of Scope:**
  - 交易服務一側的授權流程、外掛一側的連線與續用（另兩個切片，依共識契約並行開發）。
  - 在同意頁上換一個帳號（要換就先登出，再從 Claude Code 重新連線）。
  - 列出或撤銷已經授權過的外掛。
  - 只授權部分功能（這一版一律全部功能）。
  - 登入在同意頁上途中完全失效（續用也救不回來）時記住這張請求——照操作台既有做法回登入畫面；請求十分鐘內失效，重新連線即可。
  - 待開通的人開通後自動回到這張請求——開通通常遠超過十分鐘。

---

## 2. User Personas

- **Primary Role(s):** 操作台的使用者（已建立帳號的交易者），正在 Claude Code 裡把交易服務接成外掛。
- **Usage Context:** 桌機為主。他在終端機裡操作 Claude Code，Claude Code 開啟瀏覽器分頁把他送到這一頁；
  決定完之後，他回到終端機繼續。整個過程通常一分鐘內完成，授權請求最多只活十分鐘。

---

## 3. User Stories & Acceptance Criteria

### US-01 — 先登入，登入後回到同一張授權請求 [priority: P0]
**As a** 沒登入或還沒開通的使用者，**I want** 被送到登入畫面、登入後回到剛才那一張授權請求，**so that** 我不必回頭再從 Claude Code 連一次。

```gherkin
Scenario: 沒登入時先登入，登入後回到同一張授權請求
  Given 使用者沒有登入
  And 外掛替他開了授權請求「甲」
  When 他被送到外掛授權同意頁
  Then 他先看到登入畫面
  And 登入成功之後回到外掛授權同意頁，看到的是授權請求「甲」

Scenario: 已登入且已放行時直接看到同意頁
  Given 使用者已登入且已放行
  When 他被送到授權請求「甲」的外掛授權同意頁
  Then 他直接看到授權請求「甲」的同意內容

Scenario: 待開通的人看不到同意頁
  Given 使用者已登入但還在等待開通
  When 他被送到外掛授權同意頁
  Then 他被帶到等待開通那一頁
  And 看不到允許與拒絕
```

### US-02 — 看清楚是誰要什麼，親手決定 [priority: P0]
**As a** 已登入且已放行的使用者，**I want** 在同意頁上看到提出要求的外掛、我目前的帳號、以及允許之後它能做什麼，**so that** 我知道自己正把什麼交給誰。

```gherkin
Scenario: 同意頁說清楚外掛、帳號與授權範圍
  Given 授權請求「甲」由外掛「Claude Code」提出
  And 目前登入者是 james@example.com
  When 他打開授權請求「甲」的同意頁
  Then 他看到外掛名稱「Claude Code」
  And 看到帳號 james@example.com
  And 看到「允許後，它能以你的身分使用交易服務的全部功能」
  And 看到「允許」與「拒絕」兩個選擇

Scenario: 什麼都不按就什麼都不會被決定
  Given 他打開了授權請求「甲」的同意頁
  When 他什麼都不按，或重新整理頁面
  Then 授權請求「甲」沒有被允許也沒有被拒絕
  And 頁面仍顯示「允許」與「拒絕」等他選
```

### US-03 — 允許或拒絕，結果交回外掛 [priority: P0]
**As a** 在同意頁上的使用者，**I want** 按下允許或拒絕之後由外掛接手，**so that** 我回到 Claude Code 就能繼續（或知道它被拒絕了）。

```gherkin
Scenario: 允許之後交回外掛
  Given 授權請求「甲」仍有效
  When 他按下「允許」
  Then 授權請求「甲」被允許
  And 瀏覽器被送回外掛那一側
  And 頁面顯示「可以關掉這個分頁，回到 Claude Code」

Scenario: 拒絕之後交回外掛
  Given 授權請求「甲」仍有效
  When 他按下「拒絕」
  Then 授權請求「甲」被拒絕
  And 瀏覽器被送回外掛那一側，外掛得知被拒絕
  And 頁面顯示「可以關掉這個分頁，回到 Claude Code」

Scenario: 決定送出後不能再按第二次
  Given 他剛按下「允許」，結果還沒回來
  When 他再按「允許」或按「拒絕」
  Then 兩個選擇都按不下去
  And 只有第一次的決定被送出
```

### US-04 — 失效的說失效，連不上的說連不上 [priority: P0]
**As a** 使用者，**I want** 在請求已失效或交易服務連不上時得到正確的下一步，**so that** 我不會對一張死掉的請求一直按，也不會把暫時連不上誤會成要重來。

```gherkin
Scenario: 過期或已被決定過的請求
  Given 授權請求「甲」已過期（超過十分鐘）或已被決定過
  When 他打開授權請求「甲」的同意頁
  Then 他看到「這一張授權請求已失效或已被使用，請回到 Claude Code 重新連線」
  And 看不到「允許」與「拒絕」

Scenario: 網址上沒有授權請求
  Given 網址上沒有帶任何授權請求
  When 他打開外掛授權同意頁
  Then 他看到「這一張授權請求已失效或已被使用，請回到 Claude Code 重新連線」
  And 看不到「允許」與「拒絕」

Scenario: 停在頁面上太久才按允許
  Given 他打開同意頁時授權請求「甲」仍有效
  And 他停在頁面上直到請求失效
  When 他按下「允許」
  Then 他看到「這一張授權請求已失效或已被使用，請回到 Claude Code 重新連線」
  And 瀏覽器沒有被送回外掛那一側

Scenario: 打開頁面時連不上交易服務
  Given 交易服務沒有回應
  When 他打開授權請求「甲」的同意頁
  Then 他看到連不上交易服務的說明與「再試一次」
  And 不被告知請求已失效

Scenario: 按下允許時連不上交易服務
  Given 他在授權請求「甲」的同意頁上
  And 交易服務沒有回應
  When 他按下「允許」
  Then 他看到連不上交易服務的說明
  And 「允許」與「拒絕」恢復可以按
  And 瀏覽器沒有被送回外掛那一側
```

## 4. Business Flow & Logic

- **Flow:**
  外掛開出授權請求 → 瀏覽器來到同意頁（帶著請求識別）→〔沒登入〕登入畫面 → 登入成功回到同意頁
  →〔待開通〕等待開通那一頁（流程在此停止）→ 讀取請求：有效則顯示同意內容；失效則顯示「已失效」
  → 使用者按「允許」或「拒絕」→ 交易服務回覆要送往外掛的位址 → 瀏覽器整頁前往那裡 → 同意頁顯示「可以關掉這個分頁」。
- **Core Business Rules:**
  - **這一頁要先登入且已放行**；由操作台既有的門把關，這一頁不另立例外。門記下的目的地必須含授權請求識別。
  - **絕不自動允許**：只有使用者按下「允許」才送出允許；打開、重新整理都只讀取。
  - **允許要以使用者身分送出**；拒絕不需要身分（任何人都能替自己不要的請求按拒絕）。
  - **同一張請求只被決定一次**：送出期間兩個選擇都停用；結果回來且被送回外掛之後不再顯示選擇。
  - **失效只有一句話**：過期、已被決定過、不存在、網址沒帶識別，對使用者的下一步都一樣——回 Claude Code 重新連線。
  - 送回外掛是**整頁前往外掛給的位址**（外掛在使用者自己電腦上等著），不是操作台內的換頁。
- **Edge Cases:**
  - 讀取時連不上 → 說連不上並給「再試一次」，不說失效。
  - 送出決定時連不上或交易服務出錯 → 說明原因，選擇恢復可按，可再試。
  - 送出決定時請求已失效 → 換成「已失效」畫面，不送回外掛。
  - 送出允許時登入過期 → 照操作台既有做法先自己救回再重送；救不回來則回登入畫面（見 Out of Scope）。

## 5. UI/UX Design & Interaction

- **Prototype Link:** N/A（沿用登入頁／等待開通頁的卡片外型）。
- **Key Interactions:**
  - 版面：**不套用操作台外框**，置中的一張卡片，與登入頁、等待開通頁同一類。
  - 標題「授權外掛」；說明外掛名稱、目前帳號、授權範圍（全部功能）；「允許」為主要動作、「拒絕」為次要動作，並排。
  - 讀取中：卡片上顯示讀取中，不顯示選擇。
  - 送出中：兩個選擇停用，按下的那一個顯示進行中。
  - 完成：「已交回 Claude Code，可以關掉這個分頁，回到 Claude Code。」
  - 失效：「這一張授權請求已失效或已被使用，請回到 Claude Code 重新連線。」
  - 連不上：連不上交易服務的說明＋「再試一次」。
  - 全部文字繁體中文；窄螢幕（390 像素）下動作鍵完整可見，不需左右拖動。

## 6. Non-Functional Requirements

- **Performance:** 讀取與送出各只要一次往返；無額外等待。
- **Security:** 絕不自動允許；允許必須帶著目前登入者身分；不在網址或瀏覽器儲存留下任何授權結果；
  不另立任何設定項目（沿用既有的交易服務位址）。
- **Compatibility:** 與操作台其他頁面相同。
- **Analytics / Tracking:** N/A。

---

## 7. Dependencies & Risks

- **External Dependencies:** 交易服務新增的三件事（讀一張授權請求、允許、拒絕）與外掛一側的授權流程；依共識契約並行開發。
- **Known Risks:**
  - 交易服務尚未上線時這一頁無法端對端驗證；以契約描述的回覆為準。
  - 若門日後改成只記路徑不記完整網址，登入後會丟失請求識別——以驗收情境釘住。
