# Product Requirements Document (PRD)

**Feature:** 策略機器人積木工作台
**Status:** Draft
**Version:** v1.0
**Owner:** James Hsueh
**Stakeholders:** Engineering

---

## 1. Background & Goal (Why & Goal)

- **Problem Statement:**
  拼一台策略機器人目前發生在一個對話框裡，而對話框裝不下它。
  一台機器人是三段，第三段是**兩棵可以巢狀三層的樹**，
  使用者只能在一個浮在清單上的框裡捲上捲下，一邊記住上面寫過什麼。

  這帶來兩個實際的損失。

  第一，**兩棵樹看不見彼此**。買入與賣出同時成立時，這台機器人什麼都不會說，
  而且會一直不說下去——使用者是在跑了整天、一則訊息都沒收到之後才發現的。
  兩棵樹要是在同一頁上，他在拼的當下就看得見。

  第二，**看不出哪裡還沒拼完**。空著的地方就是一片空白，
  而空白跟「這裡本來就不需要東西」長得一模一樣。

- **Expected Outcome:**
  1. 拼一台機器人在**它自己的頁面**上進行，買入與賣出兩棵樹**同時看得見**。
  2. 還沒填的位置是一個**畫出來的洞**，不是空白——看得出「這裡少一塊」。
  3. 放一塊積木有**點按**與**拖拉**兩條路，兩條都走得通。
  4. 每一塊積木**自己說得出**它填完了沒有、它指的來源還在不在。
  5. 拼得出來的形狀**一定是存得下去的形狀**——放不進去的地方就是不接受。
  6. 舊的對話框**整個消失**，不留第二個入口。

- **Out of Scope:**
  - **在前端求值條件樹。** 哪一邊成立永遠是後端的答案。
  - **任何後端改動。** 存的形狀與規則全部不變。
  - **自由畫布與連線。** 條件是一棵樹不是一張圖；連線畫得出樹畫不出來的東西，
    而那些只能在儲存時被拒絕。
  - 縮放、平移、小地圖、復原／重做。
  - 鍵盤搬移積木。
  - 條件範本、複製一整棵樹、機器人之間互相複製。

## 2. User Personas

- **主要使用者：** 這個系統唯一的使用者，自己寫策略、自己拼機器人、自己看結果。
- **使用情境：** 桌機、滑鼠、一次專心拼一台。拼完就離開，靠 Telegram 收結果。
- **他知道什麼：** 知道自己每一支策略在算什麼，知道且與或的差別。
- **他不想做的事：** 記住上一段填了什麼、數括號、按了儲存才知道哪裡錯。

## 3. Acceptance Criteria

### Story A：在它自己的頁面上拼

> 身為使用者，我想在一整頁上拼一台機器人，這樣我才看得到我拼的全部。

```gherkin
Scenario: 從清單編輯一台既有的機器人
  Given 清單上有一台名為「早盤突破」的已停止機器人
  When 使用者按它的編輯
  Then 畫面走到一個屬於這一台的頁面
  And 頁面說得出現在改的是「早盤突破」
  And 它的信號來源與兩棵條件樹都是存進去時的樣子

Scenario: 從清單新拼一台
  Given 使用者在機器人清單上
  When 使用者按新增
  Then 畫面走到一張空白的頁面
  And 買入條件顯示一個空的位置
  And 賣出條件顯示一個空的位置

Scenario: 存好了就回清單並說一聲
  Given 使用者在一台機器人的頁面上，每一塊都填好了
  When 使用者按儲存
  Then 那一台被存起來
  And 畫面回到機器人清單
  And 畫面說一聲更改成功

Scenario: 改到一半想離開要先問過
  Given 使用者在頁面上放了一塊積木，還沒儲存
  When 使用者想離開這一頁
  Then 畫面先問他要不要放棄
  And 他說不放棄時，留在原地，剛剛放的那一塊還在

Scenario: 什麼都沒改就離開不問
  Given 使用者打開一台機器人的頁面，一個字都沒改
  When 使用者想離開這一頁
  Then 畫面直接讓他走，不問

Scenario: 打開一台已經不在的機器人
  Given 有一台機器人在別的地方被刪掉了
  When 使用者想打開它的頁面
  Then 畫面說找不到這一台
  And 畫面回到機器人清單

Scenario: 舊的對話框不存在了
  Given 使用者在機器人清單上
  When 使用者按新增或按任何一台的編輯
  Then 畫面走到頁面
  And 清單上不會浮出任何拼機器人的對話框
```

### Story B：把積木放進洞裡

> 身為使用者，我想看到哪裡少一塊，並且放得進去，這樣我才不用猜。

```gherkin
Scenario: 空的條件顯示一個洞
  Given 使用者在一張空白的頁面上
  When 使用者看買入條件
  Then 那裡是一個明顯可以放東西的位置
  And 它說得出可以放一塊進來

Scenario: 點一下洞就看得到放得進去的東西
  Given 買入條件是一個空的位置
  And 已宣告來源 A 與 B
  When 使用者點那個位置
  Then 積木抽屜亮起這一刻放得進去的每一塊
  And 抽屜裡有「A 等於…」與「B 等於…」
  And 抽屜裡有「全部成立」與「任一成立」

Scenario: 點抽屜裡的一塊就放進去
  Given 買入條件是一個空的位置，而使用者已經點了它
  When 使用者點抽屜裡的「A 等於…」
  Then 買入條件變成一句以 A 為對象的比對
  And 那一句的信號還沒選

Scenario: 從抽屜拖一塊到洞上
  Given 買入條件是一個空的位置
  When 使用者從抽屜把「全部成立」拖到那個位置上
  Then 買入條件變成一個全部成立的群組
  And 那個群組裡有兩個空的位置

Scenario: 把一塊搬到別的位置
  Given 一個全部成立的群組裡有一句「A 等於買入」與一個空的位置
  And 賣出條件是一個空的位置
  When 使用者把「A 等於買入」拖到賣出條件那個位置上
  Then 賣出條件變成那一句「A 等於買入」
  And 它原本待的位置變回一個空的位置

Scenario: 搬一個群組是搬走它底下的一整串
  Given 買入條件是一個群組，裡面有一個任一成立的群組，那裡面有兩句比對
  When 使用者把裡面那個任一成立的群組搬到別的位置
  Then 那兩句比對跟著一起走
  And 它們之間的層次沒有改變

Scenario: 拿掉一塊
  Given 買入條件的群組裡有一句「A 等於買入」
  When 使用者拿掉那一句
  Then 它不見了
  And 它待過的位置變回一個空的位置

Scenario: 拿掉一個群組是拿掉它底下的一整串
  Given 買入條件是一個群組，裡面有三句比對
  When 使用者拿掉那個群組
  Then 那三句跟著一起不見
  And 買入條件變回一個空的位置

Scenario: 深度到頂就放不進群組
  Given 一個巢狀深度已經到上限的群組，裡面有一個空的位置
  When 使用者點那個位置
  Then 抽屜裡的群組那一類放不進去
  And 畫面說得出巢狀已經到最深

Scenario: 節點數到頂就什麼都放不進去
  Given 一棵樹的節點總數已經到上限
  When 使用者點任何一個空的位置
  Then 抽屜裡沒有任何一塊放得進去
  And 畫面說得出這台機器人的條件已經到上限

Scenario: 一個來源都還沒宣告
  Given 使用者還沒宣告任何信號來源
  When 使用者看積木抽屜
  Then 比對那一類是空的
  And 抽屜說得出要先宣告一個信號來源
```

### Story C：每一塊自己說得出狀態

> 身為使用者，我想在放的當下就知道哪一塊還有問題，而不是按了儲存才知道。

```gherkin
Scenario: 群組還不夠兩塊
  Given 一個全部成立的群組裡只放了一句比對
  When 使用者看那個群組
  Then 那個群組自己標出還沒填完
  And 它說得出一個群組至少要兩塊

Scenario: 比對還沒選信號
  Given 一句比對已經指名來源 A，但還沒選信號
  When 使用者看那一句
  Then 那一句自己標出還沒填完

Scenario: 比對指向一個不存在的來源
  Given 買入條件裡有一句「A 等於買入」
  When 使用者把來源 A 的代號改成 C
  Then 那一句跟著變成「C 等於買入」

Scenario: 一個還被條件用著的來源刪得掉，只是先說一聲
  Given 買入條件裡有一句「A 等於買入」
  And 來源 A 是這台機器人唯一的來源
  When 使用者看那個來源
  Then 畫面說得出條件裡還在用它
  And 移除那個來源仍然按得動

Scenario: 來源被刪掉之後那一句自己說
  Given 買入條件裡有一句「A 等於買入」
  When 使用者把來源 A 刪掉
  Then 那一句自己標出它指向一個已經不存在的來源
  And 它的標示與「還沒填完」不是同一種
  And 這台機器人送不出去

Scenario: 把樹上的一塊拖出去丟掉
  Given 買入條件的群組裡有三句比對
  When 使用者拖起其中一句
  Then 畫面出現一個可以把它丟掉的位置
  And 放開之後那一句不見了，另外兩句還在

Scenario: 從抽屜拖出來的那一塊丟不掉
  Given 使用者從積木抽屜拖起一塊
  When 他看畫面
  Then 那個丟掉用的位置不出現——那一塊本來就不在樹上

Scenario: 代號改成一個正被別人用著的字，那一句自己說
  Given 已宣告來源 A 與 B，買入條件裡有一句「A 等於買入」
  When 使用者把 A 的代號改成 B
  Then 那一句仍然指著 A，不會跟著併到 B 上
  And 那一句自己標出它指向一個已經不存在的來源
  And 它的標示與「還沒填完」不是同一種

Scenario: 每一塊都好了就沒有任何標示
  Given 買入與賣出兩棵樹的每一塊都填好了
  When 使用者看這兩棵樹
  Then 沒有任何一塊被標成有問題

Scenario: 存不下去的時候看得出來
  Given 買入條件裡還有一個空的位置
  When 使用者看儲存
  Then 儲存按不下去
  And 畫面說得出還有哪一件事沒好
```

### Story D：兩棵樹在同一頁

> 身為使用者，我想同時看到買入與賣出，這樣我才看得出它們會不會撞在一起。

```gherkin
Scenario: 兩棵同時看得見
  Given 一台買入與賣出都拼好的機器人
  When 使用者打開它的頁面
  Then 買入條件與賣出條件同時出現在畫面上
  And 不必切換分頁或展開才看得到另一棵

Scenario: 改一棵不會動到另一棵
  Given 買入與賣出各有一句比對
  When 使用者在買入條件裡再放一塊
  Then 賣出條件一個字都沒變
```

### Story E：來源與抽屜連動

> 身為使用者，我想改了來源之後抽屜立刻跟上，這樣抽屜列的就是現在拼得出來的東西。

```gherkin
Scenario: 加一個來源，抽屜立刻多一塊
  Given 已宣告來源 A
  When 使用者加一個代號為 B 的來源
  Then 抽屜裡立刻多出「B 等於…」

Scenario: 刪一個來源，抽屜立刻少一塊
  Given 已宣告來源 A 與 B
  When 使用者把 B 刪掉
  Then 抽屜裡只剩「A 等於…」

Scenario: 改代號，抽屜與樹上的比對一起跟著改
  Given 已宣告來源 A，買入條件裡有一句「A 等於買入」
  When 使用者把 A 的代號改成 C
  Then 抽屜裡是「C 等於…」
  And 買入條件那一句變成「C 等於買入」
```

## 4. Core Business Rules

| # | Rule |
|---|---|
| BR-1 | 一個條件要嘛是**一句比對**（一個來源代號＋一個信號），要嘛是**一個群組**（且／或＋兩個以上的子條件）。沒有第三種。 |
| BR-2 | 買入條件與賣出條件**都不得為空**。 |
| BR-3 | 一句比對指名的來源代號，必須是這一台機器人**已宣告的其中之一**。 |
| BR-4 | 一個群組**至少兩個**子條件。 |
| BR-5 | 巢狀深度與節點總數沿用既有上限，**這一刀不改動**。 |
| BR-6 | 使用者**放得出來的形狀，一定是存得下去的形狀**——超過巢狀深度或節點數的位置不接受積木，而不是接受了再於儲存時拒絕。**內容**沒填完（空群組、還沒選信號）是另一回事：那是刻意允許的中間狀態，每一塊自己標出來，並由儲存擋下且說得出是哪一塊。 |
| BR-7 | 搬移或拿掉一個群組，是搬移或拿掉**它底下的一整串**，不拆開。 |
| BR-8 | 來源代號改名時，樹上每一句指向它的比對**一起跟著改**；改名經過一個與別人撞名的瞬間時不改，等它不再撞名才改。 |
| BR-9 | **前端不求值條件樹。** 哪一邊成立永遠是後端在跑一輪時的答案。 |
| BR-10 | 拼一台機器人**只有一個入口**：它自己的頁面。 |

## 5. UI/UX

- **一列加兩欄。** 最上面一列是「這台機器人是什麼」（名稱、標的、每隔幾分鐘）——
  填一次就不會再動的東西不該佔著高度。底下兩欄：左邊積木，右邊兩棵樹。
  窄畫面時上下堆疊，積木排在樹上面（積木要在手邊，不是捲到底才拿得到）。
- **信號來源就是積木，不是另一份清單。** 一個來源＝一塊積木，上面寫的是
  **那支策略的名字**；它自己的設定（代號、策略、刻度、旋鈕）收在它底下，
  按齒輪才打開。收起來時一個來源就是一行——十個來源仍然是十行，
  而不是把工作區推出畫面。
- **代號的預設值是那支策略的名字**（撞名時接數字），
  所以條件讀起來是「MACD 交叉 等於 買入」，而不是「A 等於 買入」。
- **兩棵樹上下排**，各自有整欄的寬度——條件已經會到三層深，寬度比並排重要。
- **樹上每一塊的抓把是一條完整高度的直條**，不是一個小圖示：
  裡面那幾個下拉選單會吃掉滑鼠事件，從它們身上按下去拖不動任何東西——
  抓的地方必須大到不用瞄準。
- **空的位置畫成一個看得出可以放東西的框**，裡面一句話說「放一塊進來」。
- **積木抽屜固定在工作區左邊，一直在那裡。** 它不會自己收起來，
  也沒有任何一種「要先做什麼才看得到它」的狀態——積木式編輯器一向如此
  （Scratch 的積木面板固定在左側；Blockly 的 toolbox 是 always displayed）。
  **不做成滑過去才出現的抽屜**：那個模式在選單設計上早有定論——
  使用者失去控制權（他沒打算打開，它自己開了），而且用鍵盤與觸控的人根本碰不到。
- 抽屜**黏住**，不隨著樹愈拼愈長而捲出畫面。「被樹推走」真正的答案是這個，
  不是把它藏起來。積木多到裝不下時，捲的是它自己，不是整頁。
- 點了某個空位之後，抽屜裡**放得進去的那幾塊亮起來**。
- **未完成**與**指向不存在的來源**用**兩種不同的標示**：
  前者是「還沒做完」，後者是「有東西壞了」，使用者的下一步不一樣。
- **載入中**：頁面在讀那一台的時候說它在讀。
- **空狀態**：一個來源都沒有時說得出下一步；一支會吐訊號的策略都沒有時說的是另一件事
  （要先去策略庫建一支）——兩件事的下一步不同。
- **錯誤**：後端拒絕時，頁面留著，照它說的那句話講。

## 6. Non-Functional Requirements

| # | Requirement |
|---|---|
| NFR-1 | 拖拉與點按**兩條路都要能完成同一件事**；只支援其中一條不算做完。 |
| NFR-2 | 每一次編輯產生一棵**新的樹**，不就地改動舊的——上一個狀態始終完整。 |
| NFR-3 | 頁面在**沒有指標裝置**的情況下仍可用（點按那條路不依賴拖拉）。 |
| NFR-4 | 兩棵樹各自獨立：對一棵的任何操作都不得改到另一棵。 |

## 7. Dependencies & Risks

- **依賴**：既有的策略機器人存取能力、可用策略清單、彙總刻度、策略參數，全部不動。
- **風險**：拖拉在巢狀結構裡容易放錯層。**緩解**：只有可放的位置接受，
  而且點按那條路不經過拖拉。
- **風險**：整頁取代對話框之後，清單那一頁的測試會有一批要跟著改。
  **緩解**：清單本身的行為不變，改的只是按下編輯之後走去哪裡。
