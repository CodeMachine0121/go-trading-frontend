## 1. Background & Goal (Why & Goal)

### Problem Statement

後端的回測現在會收手續費了，而這個畫面**填不出那兩個費率**。

使用者在這裡做的事是一圈一圈的：跑一支、看成績單、調一調、再跑一支。
而他每一次看到的成績單，描述的都是一個**交易免費**的世界。

| 一支不賺不賠的策略，本金一百萬 | 畫面會說 | 實際上會剩 |
|---|---:|---:|
| 一年進出 4 趟 | 100 萬 | 98.1 萬 |
| 一年進出 200 趟 | 100 萬 | **38.9 萬** |

偏差與交易次數成正比，所以**交易頻繁的那一支被高估最多，而它看起來最漂亮**。
他一直在用一把會偏心的尺量兩件東西，而畫面上沒有任何東西告訴他這件事。

### Expected Outcome

兩張重演表單各多一組「交易成本」；成績單多一格累計成本；
交易明細每一列看得到自己的兩筆成本。全部留白時，畫面與這一刀之前一模一樣。

### Out of Scope

| 不做 | 為什麼 |
|:---|:---|
| 畫面自己算任何成本 | 累計成本、逐筆成本、淨額全部由後端算。這裡多算一次就是多一個會不一致的數字 |
| 把費率記在策略腳本或交易策略身上 | 與初始資金、出場價位同一類，跟著這一次走 |
| 每筆最低手續費 | 後端不支援 |
| 預填一組常見費率 | 預設值就是替使用者改掉了他的成績單 |

## 3. User Stories & Acceptance Criteria

### US-01 — 兩張表單都填得出那兩個費率 [priority: P0]

> **作為** 策略調校者
> **我想要** 在重演的表單上填進場與出場的成本率
> **以便** 成績單算的是我真的要付錢去跑的那個策略

**Acceptance Criteria**

- **AC-01.1** 兩張重演表單都有一組「交易成本」：進場成本率、出場成本率兩格併排。
- **AC-01.2** 兩格**預設留白**，留白即完全不計。
- **AC-01.3** 那一組旁邊要說出：**留白就不計**，以及**出場留白時沿用進場**。
- **AC-01.4** 兩張表單的那一組**一字不差**（來自同一個共用元件）。
- **AC-01.5** 兩格佔滿整列，不與其他欄位擠在同一格——與出場價位同一個理由。

```gherkin
Scenario: 兩張重演表單都有那一組
  Given 使用者打開重演一支策略腳本的表單
  When 他看那一整排條件
  Then 他看得到「交易成本」那一組，兩格都是空的
  And 他讀得到留白就不計
  And 他讀得到出場留白時沿用進場

Scenario: 重演一份交易策略的表單長得一模一樣
  Given 使用者打開重演一份交易策略的表單
  Then 他看得到同樣那一組，兩格都是空的
```

### US-02 — 講不通的費率不送出，訊息標在那一組旁邊 [priority: P0]

> **作為** 策略調校者
> **我想要** 填錯的時候當場知道，而且知道是哪一格
> **以便** 我不用送一次出去才發現，也不用猜要改哪裡

**Acceptance Criteria**

- **AC-02.1** 任一費率**為負** → 不送出，訊息標在「交易成本」那一組旁邊。
- **AC-02.2** 任一費率**超過 100** → 同上。
- **AC-02.3** 訊息**說得出是進場還是出場那一格**（一則訊息蓋住兩格，由句子本身說）。
- **AC-02.4** 正好 100 → 送得出去。
- **AC-02.5** 後端指名那一組時，訊息標在**同一組旁邊**，不是變成一句籠統的拒絕。

```gherkin
Scenario: 負的費率不送出
  Given 使用者把進場成本率填成 -1
  When 他按下執行回測
  Then 請求沒有送出
  And 交易成本那一組旁邊出現一則訊息，說出進場成本率不得為負

Scenario: 超過一百的費率不送出
  Given 使用者把出場成本率填成 101
  When 他按下執行回測
  Then 請求沒有送出
  And 交易成本那一組旁邊出現一則訊息，說出出場成本率不得超過 100%

Scenario: 正好一百送得出去
  Given 使用者把進場成本率填成 100
  When 他按下執行回測
  Then 請求送出

Scenario: 後端指名那一組時訊息落在同一個地方
  Given 後端以交易成本那一組為由拒絕這次重演
  When 畫面收到那個拒絕
  Then 訊息出現在交易成本那一組旁邊
```

### US-03 — 留白時畫面與這一刀之前一模一樣 [priority: P0]

> **作為** 策略調校者
> **我想要** 不填費率時什麼都不變
> **以便** 我手上既有的每一張成績單仍然讀得懂

**Acceptance Criteria**

- **AC-03.1** 兩格留白時，送出去的請求**不含那兩格**（不送零）。
- **AC-03.2** 只填進場時，送出去的請求**只含進場那一格**。
- **AC-03.3** 沒收過錢時，成績單**不出現**累計成本那一格。
- **AC-03.4** 沒收過錢時，交易明細**不出現**那兩欄成本。

```gherkin
Scenario: 留白不上線
  Given 使用者兩格都留白
  When 他按下執行回測
  Then 送出去的請求裡沒有進場成本率，也沒有出場成本率

Scenario: 只填一格就只送一格
  Given 使用者只填了進場成本率 0.1
  When 他按下執行回測
  Then 送出去的請求裡有進場成本率，沒有出場成本率

Scenario: 沒收過錢的成績單不多出格子
  Given 這次重演的累計成本是零
  When 使用者讀成績單
  Then 沒有累計成本那一格
  And 交易明細沒有成本那兩欄
```

### US-04 — 成績單與明細說得出那筆錢 [priority: P0]

> **作為** 策略調校者
> **我想要** 看到這次總共付了多少、每一筆付了多少
> **以便** 我判斷這支策略是抓價差不行，還是被手續費吃掉

**Acceptance Criteria**

- **AC-04.1** 收過錢時，成績單出現**累計成本**那一格。
- **AC-04.2** 收過錢時，交易明細每一列看得到它自己的**進場成本**與**出場成本**。
- **AC-04.3** 賺賠那一欄**已經是淨額**，畫面要說出這件事。
- **AC-04.4** 金額的寫法與畫面上其他金額**一字不差**（同樣的進位規則）。

```gherkin
Scenario: 收過錢的成績單多一格
  Given 這次重演付掉了 210 元
  When 使用者讀成績單
  Then 他看得到累計成本 210.00

Scenario: 收過錢的明細多兩欄
  Given 一筆交易付了 100 進場、110 出場
  When 使用者讀交易明細
  Then 那一列看得到 100.00 與 110.00
  And 賺賠那一欄是扣掉這兩筆之後的淨額
```

### US-05 — 成績單說得出開了幾次倉，明細的空狀態說實話 [priority: P0]

> **作為** 策略調校者
> **我想要** 在還抱著部位的時候看得出來
> **以便** 我不會把「開了還沒平」誤讀成「腳本從頭到尾沒開口」

**背景**：一支每一棒都說買入的腳本，會開一注抱到最後。那一注不是已平倉交易，
所以交易次數是 0、明細是空的——但它的進場成本付掉了、市值算進最後剩多少。
在有交易成本之前這張畫面是自洽的；有了成本之後它自相矛盾：
**沒有交易，錢卻付出去了**。而明細那句空狀態還給了一個與事實相反的理由。

**Acceptance Criteria**

- **AC-05.1** 成績單多一格**開倉次數**，**一律顯示**（不是「大於零才出現」——
  它與交易次數同一個層級的基本事實，而它等於零本身就是資訊）。
- **AC-05.2** 開倉次數擺在交易次數旁邊。
- **AC-05.3** 還抱著一注沒平時，明細的空狀態**不得**說「沒有觸發任何交易」，
  要說出那一注還開著、所以不在明細裡。
- **AC-05.4** 真的一次都沒開倉時，空狀態維持**現在那句一字不差**。
- **AC-05.5** 「還抱著一注」這件事由領域決定，不由元件自己從數字推。

```gherkin
Scenario: 每一棒都說買入，開了一注抱到最後
  Given 一次重演開倉 1 次、平倉 0 次
  When 使用者讀成績單
  Then 開倉次數是 1
  And 交易次數是 0

Scenario: 那張空明細要說出真正的原因
  Given 一次重演開倉 1 次、平倉 0 次
  When 使用者讀交易明細
  Then 他讀得到還有一注沒有平倉，所以不在這張明細裡
  And 他讀不到「沒有觸發任何交易」

Scenario: 真的一次都沒開倉時說法不變
  Given 一次重演開倉 0 次、平倉 0 次
  When 使用者讀交易明細
  Then 他讀到「這段期間沒有觸發任何交易。算式可以從頭到尾都說持平，這不算失敗。」

Scenario: 開幾次平幾次都說得出來
  Given 一次重演開倉 4 次、平倉 4 次
  When 使用者讀成績單
  Then 開倉次數是 4
  And 交易次數是 4
```

## 4. Business Flow & Logic

```
使用者填兩格（或留白）
  → 送出前驗證（負、超過 100 → 不送出，訊息標在那一組旁邊）
  → 只把真的填了的那幾格放進請求
  → 後端算完回成績單
  → 畫面照後端給的數字畫，一個都不自己算
```

### Core Business Rules

| # | 規則 |
|:---|:---|
| R-1 | 兩格選填；留白即不計；出場留白沿用進場（由後端執行，畫面只說明） |
| R-2 | 負、超過 100 一律不送出；正好 100 送得出去 |
| R-3 | 拒絕指向**一格**（那一組），句子說出是哪一個費率 |
| R-4 | 留白的那一格**不進請求主體**——零是空輸入框的產物，不是使用者的意思 |
| R-5 | 累計成本與明細那兩欄，**沒收過錢就不顯示** |
| R-6 | 畫面一個數字都不算 |
| R-7 | 開倉次數一律顯示；「還抱著一注」＝開倉次數大於已平倉筆數（同一時間最多一個部位），由領域判斷 |

### Edge Cases

| 情況 | 行為 |
|:---|:---|
| 兩格留白 | 請求不含那兩格；成績單與明細不多任何東西 |
| 只填一格 | 只送那一格 |
| 填了非數字 | 與其他數字欄位同一條規則：說「請填一個數字」 |
| 一次都沒開倉 | 明細照舊那一句；累計成本是零 |
| 開了一注沒平 | 明細說出那一注還開著；交易次數 0、開倉次數 1；累計成本只含已付的進場成本 |

## 5. UI/UX Design & Interaction

| 位置 | 樣子 |
|:---|:---|
| 兩張重演表單 | 「交易成本」一組，佔滿整列，兩格併排，旁邊一句「留白就不計。出場留白時跟進場一樣」 |
| 成績單 | 收過錢時多一格「交易成本」 |
| 交易明細 | 收過錢時多兩欄「進場成本」「出場成本」，擺在「賺賠」之前 |
| 賺賠欄 | 表頭寫明是扣掉成本後的淨額 |
| 成績單 | 交易次數旁邊多一格「開倉次數」，一律顯示 |
| 交易明細空狀態 | 還抱著一注時換一句話，說出那一注還開著 |

## 6. Non-Functional Requirements

| 項目 | 要求 |
|:---|:---|
| 相容性 | 兩格留白時，畫面的每一個既有斷言逐字不變 |
| 一致性 | 兩張表單的那一組來自同一個元件，不可能只改到一邊 |
| 分層 | 驗證在 Domain Model，格式化在 Domain Model，元件只畫 |

---

## 7. Dependencies & Risks

| 項目 | 說明 | 對策 |
|:---|:---|:---|
| 後端要先支援 | 那兩格與三個新數字都是後端算的 | 後端先落地 |
| 明細再多兩欄會更寬 | 表格已經七欄 | 沒收過錢就不顯示，所以既有的每一次重演寬度不變 |
