## 1. Background & Goal (Why & Goal)

### Problem Statement

助手的等待狀態活在瀏覽器分頁裡（`useState('assistant-pending')`）。整頁重新載入就沒了，
而使用者最可能重整的時機，正是他等最久、最懷疑畫面壞掉的那一刻。

助手現在會在一次回答裡拼交易策略、回測、改、再回測——**可能好幾分鐘**。
重整一次，他看到一片空白，以為沒送出去，再問一次，付第二次錢。

### Expected Outcome

- 等待狀態**改成問後端**：那一段對話最後一則的狀態是不是進行中。
- 重整、關分頁、切走再回來，看到的都是同一件事。
- 定時回頭讀那一段對話（全站一條），答完或失敗就停；換一段對話也停。
- 失敗**留在對話串上**並說得出原因，可以重試。
- 讀回來的回答帶得回「查了幾次／用量／有沒有提早收尾」。

### Out of Scope

- 推播、串流、取消進行中的那一則、多分頁同步。

---

## 2. User Personas

**Primary Role:** 已登入的使用者，本機單人使用。

**Usage Context:** 他送出一句之後**很可能離開**——切到工作檯、去泡咖啡、關掉瀏覽器。
這是整個切片存在的理由：在他不在場的那幾分鐘裡，畫面回來時要說得出發生過什麼。

## 3. User Stories & Acceptance Criteria

### US-01 — 送出之後看得到它收下了 [priority: P0]

**As a** 使用者，**I want** 送出之後馬上看到提問與等待，
**so that** 我不必盯著一個看不出有沒有送出去的畫面。

```gherkin
Scenario: 送出之後立刻看到等待
  Given 我在助手對話裡
  When 我送出一句
  Then 提問出現在對話串上
  And 它底下出現等待

Scenario: 等待是後端說的,不是畫面自己記的
  Given 後端說那一段對話最後一則還在跑
  When 畫面渲染那一段對話
  Then 等待出現
  And 畫面沒有用自己的旗標決定這件事
```

### US-02 — 重新整理之後還看得到 [priority: P0]

**As a** 使用者，**I want** 重整不會把還在寫的回答弄丟，
**so that** 我不會以為沒送出去而再問一次。

```gherkin
Scenario: 重整之後等待還在
  Given 助手正在寫一則回答
  When 我重新整理畫面並打開那一段對話
  Then 提問還在,等待也還在

Scenario: 關掉分頁再回來看得到答案
  Given 助手正在寫一則回答
  When 我關掉分頁,過幾分鐘再打開那一段對話
  Then 我看得到完整的答案

Scenario: 全部答完的對話不顯示等待
  Given 一段對話的每一則都答完了
  When 我打開它
  Then 沒有等待
```

### US-03 — 定時回來問，答完就停 [priority: P0]

**As a** 使用者，**I want** 答案寫完時畫面自己補上，
**so that** 我不必一直手動重整。

```gherkin
Scenario: 答完就自己出現
  Given 有一則回答正在寫
  When 它轉成已回答
  Then 答案出現在畫面上
  And 定時詢問停下來

Scenario: 沒有東西在跑就不問
  Given 一段對話的每一則都答完了
  When 我停在這一段上
  Then 畫面不會定時去打後端

Scenario: 切到別的畫面不會把那次回答丟掉
  Given 有一則回答正在寫
  When 我切到別的頁面,過一會兒再回來
  Then 我看得到答案

Scenario: 換一段對話就停止問舊的那一段
  Given 有一則回答正在寫
  When 我按開新對話
  Then 定時詢問停下來

Scenario: 抽屜與整頁同時活著也只問一次
  Given 有一則回答正在寫,而抽屜與整頁都在
  When 過了一個詢問間隔
  Then 後端只被問一次
```

### US-04 — 壞掉的那一次看得出來也看得出為什麼 [priority: P0]

**As a** 使用者，**I want** 失敗留在對話的那個位置，
**so that** 我好幾分鐘後回來還知道發生過什麼。

```gherkin
Scenario: 失敗顯示後端給的原因
  Given 助手不可用,那一則轉成失敗
  When 畫面讀到那一段對話
  Then 那句提問底下出現後端給的那句原因

Scenario: 重整之後原因還在
  Given 承上
  When 我重新整理
  Then 那句原因還在

Scenario: 被重新啟動中斷
  Given 系統在寫那一則的時候重新啟動了
  When 我回來看
  Then 我看得到「被重新啟動中斷,請再問一次」

Scenario: 可以再試一次
  Given 有一則失敗了
  When 我按再試一次
  Then 同一句話再送一次
```

### US-05 — 前一則還在跑的時候不能再送 [priority: P0]

**As a** 使用者，**I want** 等待中送不出第二句，
**so that** 我不會讓同一段對話同時有兩則在寫。

```gherkin
Scenario: 等待中送出鍵停用
  Given 有一則回答正在寫
  When 我看送出鍵
  Then 它是停用的
  And 輸入框仍然打得了字

Scenario: 後端拒絕時如實轉達
  Given 我在另一個分頁已經送了一句
  When 這個分頁也送出
  Then 後端拒絕
  And 那句拒絕原樣顯示出來
```

### US-06 — 讀回來的每一則說得出自己的來歷 [priority: P1]

**As a** 使用者，**I want** 看得出哪一則答完、哪一則在跑、哪一則壞了，
**so that** 一段對話讀回來是完整的事實而不是片段。

```gherkin
Scenario: 三種狀態各自的樣子
  Given 一段對話裡兩則答完、一則在跑
  When 我讀它
  Then 兩組提問加回答
  And 最後那句提問底下是等待

Scenario: 提早收尾看得出來
  Given 一則回答因為查詢次數用完而提早收尾
  When 我讀那一段對話
  Then 那則回答上看得到已達查詢次數上限
```

## 4. Business Flow & Logic

### 一次提問

```
送出一句
  ├─ 樂觀先把提問放上對話串（等待可能好幾分鐘，他要看得到自己問了什麼）
  ├─ POST /chat → 202 {conversationId, turnId, status:"running"}
  └─ 開始定時讀那一段對話
        ├─ 最後一則還在跑 → 繼續
        ├─ 最後一則已回答 → 畫出答案，停
        └─ 最後一則失敗   → 畫出原因，停
```

### 打開一段對話（含重整後）

```
讀那一段對話
  └─ 最後一則還在跑？ → 開始定時讀（這一條就是「重整之後還看得到」）
```

### Core Business Rules

| # | Rule |
|---|------|
| BR-1 | 等待狀態一律由**後端讀回來的訊息**決定，畫面不另存旗標 |
| BR-2 | 只在「有一則在跑」時定時詢問，且**全站只有一條**；答完、失敗、換對話一律停。**切換畫面不停**——助手是全站共用的一段對話 |
| BR-3 | 失敗**留在對話串上**並顯示後端給的那句原因，可重試 |
| BR-4 | 等待中送出鍵停用；輸入框不鎖 |
| BR-5 | 後端的拒絕一律**如實轉達**，不自己改寫 |
| BR-6 | 進行中與失敗的那一則**只有提問**，沒有空白的回答泡泡 |

### 為什麼等待不能留在前端

它現在是跨畫面共用的 `useState`，整頁重新載入就沒了。真相只能放在後端：
**那一段對話最後一則是不是還在跑**。畫面只是把它畫出來。

### Edge Cases

| 情境 | 行為 |
|------|------|
| 定時詢問時後端連不上 | **什麼都不說**，下一次醒來再試一次。答案還在後端那邊寫著，這一次沒讀到不代表它不見了；而跳一塊紅色警示比什麼都不說更糟——它上面那顆再試一次會再送一次同一句、再花一次錢，去修一件根本沒壞的事。等待本身已經誠實地說了「還不知道」 |
| 那一段對話在別處被刪掉 | 沿用既有行為：明說找不到並退回一段新對話 |
| 換一段對話時讀不回來 | 畫面停在本來那一段並說出原因；**本來那一段還在寫的話照樣繼續問**——不接回去的話那個答案永遠不會出現 |
| 換過去之後，本來那一段慢一步回來 | **丟掉那個結果**。取消得掉的只有「排好的下一次」，取消不掉「已經送出去的那一次」 |
| 好幾分鐘後回來、看到上次那一則壞了 | 再試一次送得出**同一句**——它就寫在畫面上，而記在畫面狀態裡的那一句早就隨重新載入沒了 |
| 送出時後端回 409 | 如實顯示那句話，不再送 |
| 一段新對話（還沒有識別碼）送出失敗 | 樂觀放上去的那一則**收回「還在寫」這個宣稱**（它留在畫面上，警示塊長在它下面）；沿用既有的警示塊與再試一次。不收回的話畫面會永遠轉圈圈，而警示塊只在不等的時候出現——使用者會看到一個沒有盡頭的等待、沒有任何說明，也送不出下一句 |
| 同一段對話開在兩個分頁 | 兩邊各自定時問，各自畫出同一件事 |

## 5. UI/UX Design & Interaction

- **等待**：沿用既有的 `AssistantPendingNotice`，長在提問底下。它現在由讀回來的
  訊息狀態驅動，而不是由本地旗標。「這一題查得比較久」那句話保留——
  現在它更有用，因為一次回答真的可能好幾分鐘。
- **失敗**：長在提問底下，外形與既有的警示塊一致，附一顆再試一次。
- **送出鍵**：等待中停用。輸入框不鎖。
- **一則回答的附註**：沿用既有的 `AssistantAnswerNoteDto` 呈現，
  現在**每一則讀回來的回答都有**，不再只有剛收到的那一則。

## 6. Non-Functional Requirements

- 定時詢問間隔寫成**一處的常數**，預設兩秒。
- 沒有東西在跑時**零輪詢**。
- **全站同時最多一條迴圈**，不因為抽屜與整頁同時活著而變成兩條。
- 迴圈**自己會停**：每次醒來重新問一次「還在寫嗎」，不是的話就不再排下一次。
  比起「在某個地方清掉它」更可靠——清的那個地方總有一天會漏掉一條路徑，
  而一條自己不會停的迴圈會一直打後端，沒有人會發現。

## 7. Dependencies & Risks

| 項目 | 說明 |
|------|------|
| 依賴 | 後端 `POST /chat` 回 202 與 `{conversationId,turnId,status}` |
| 依賴 | 後端讀一段對話時每則帶 `status`／`failureReason`／`queryCount`／`usage`／`stoppedAtQueryLimit` |
| 依賴 | 後端 409 `ErrAssistantAnswerInProgress` |
| 風險 | 輪詢在後端掛掉時空轉。它每兩秒一次、且只在有東西在寫的時候跑，代價可接受；換來的是後端回來時畫面自己補上 |
| 風險 | 一段很長的對話每兩秒整包讀回。目前單人使用、對話不長，先不優化 |

## 8. Appendix

一次回答的狀態：`running`／`answered`／`failed`，與後端一字不差。
