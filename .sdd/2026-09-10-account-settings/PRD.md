# Product Requirements Document (PRD)

**Feature:** 帳號設定畫面
**Status:** Draft
**Version:** v1.0
**Owner:** James Hsueh
**Stakeholders:** Engineering

---

## 1. Background & Goal (Why & Goal)

- **Problem Statement:**
  這個操作台認得出現在是誰在用——側欄底下就寫著他的電子郵件——
  但那個人在畫面上**找不到任何一個關於自己的地方**：
  帳號長什麼樣只有側欄那一行、密碼想換沒有地方換、
  想讓系統把訊息送到自己的 Telegram 也無從設定。
  後端這一輪長出了「換密碼」與「Telegram 投遞」兩件能力，而畫面上一顆鍵都沒有。

- **Expected Outcome:**
  操作台多一個**設定**的去處。可驗證的結果有六項：
  1. 側欄按得到「設定」，每一個畫面都到得了；沒登入的人被擋在門外。
  2. 在那裡看得到自己的**電子郵件**；密碼那一格明說**看不到，只能換**。
  3. 三格填完換得掉密碼；**兩次新密碼不一致由畫面自己擋下**。
  4. 換成功後**先說一聲**「請用新密碼重新登入」，再把人帶回登入畫面。
  5. 留得下 **Telegram 投遞設定**；存完之後**金鑰那一格是空的**，旁邊寫著結尾四碼。
  6. 按一顆「送出測試訊息」，成功說成功，失敗**說得出是四種原因的哪一種**。

- **Out of Scope:**
  - 換電子郵件、刪除帳號、停用帳號。
  - 忘記密碼（寄信重設）——後端沒有這件事。
  - 在畫面上設定「**哪些事情**要送到 Telegram」。這一刀只設定與試送。
  - 送出紀錄的清單。
  - Telegram 以外的投遞管道。
  - 顯示帳號建立時間、登入裝置清單這類其他帳號資訊。

---

## 2. User Personas

- **Primary Role(s):** **使用者**——這台操作台的主人，同時是它的唯一使用者。
- **Usage Context:**
  桌機瀏覽器、已經登入。他來這一頁通常是為了做**一件明確的事**
  （換密碼，或把 Telegram 接起來），做完就走。
  因此這一頁的每一區塊都要**自己講得完自己**，不要求他先讀完整頁才敢按。

## 3. User Stories & Acceptance Criteria

### US-01 — 從側欄走得到設定，而且只有登入的人走得到 [priority: P0]

**As a** 使用者，**I want** 在每一個畫面都按得到「設定」，
**so that** 我要調整關於自己的東西時不必記位址。

```gherkin
Scenario: 從側欄進得去
  Given 使用者已經登入
  When 他從側欄按下「設定」
  Then 畫面換到設定畫面
  And 他看到自己的電子郵件

Scenario: 沒登入的人被帶到登入畫面，登入後回到這裡
  Given 使用者沒有登入
  When 他直接打開設定畫面的位址
  Then 畫面被帶到登入畫面
  And 他登入成功後回到設定畫面，而不是首頁
```

### US-02 — 看自己的帳號，並知道密碼為什麼看不到 [priority: P0]

**As a** 使用者，**I want** 一眼看到我的帳號，並且知道密碼看不到是刻意的，
**so that** 我不會以為那一格壞了。

```gherkin
Scenario: 顯示電子郵件
  Given 使用者以「james@example.com」登入
  When 他打開設定畫面
  Then 他看到電子郵件「james@example.com」

Scenario: 密碼那一格是一排點，並直說原因
  Given 使用者已經登入
  When 他打開設定畫面
  Then 密碼那一格顯示的是一排遮住的點
  And 旁邊寫著「密碼不會顯示，只能更換」
```

### US-03 — 換密碼 [priority: P0]

**As a** 使用者，**I want** 在這一頁換掉自己的密碼，
**so that** 我懷疑舊的那一組不安全時，做得了一件事。

```gherkin
Scenario: 送出中按不了第二次
  Given 這次更換正在送出
  When 使用者再按一次更換
  Then 按鈕按不下去
  And 這次更換只被送出一次

Scenario: 換成功先說一聲再帶走
  Given 使用者三格都填對
  When 他按下更換而後端回覆成功
  Then 畫面顯示「密碼已更換，請用新密碼重新登入」
  And 之後畫面回到登入畫面
```

## 4. Business Flow & Logic

**Happy path（換密碼）**

1. 使用者在設定畫面填三格：目前的密碼、新的密碼、再打一次新的密碼。
2. 按下更換。**畫面先判兩次新密碼是否一致**，不一致就到此為止、不送出。
3. 送去後端。進行中按鈕停用。
4. 後端拒絕：把原因**掛回出問題的那一格**。
5. 後端成功：顯示「密碼已更換，請用新密碼重新登入」，然後回到登入畫面。

**Happy path（Telegram）**

1. 進入設定畫面時讀一次目前的設定：有就顯示聊天室代號與金鑰結尾，沒有就顯示「還沒有設定」。
2. 使用者填兩格並儲存 → 成功後**清空金鑰那一格**、更新顯示的結尾。
3. 使用者在測試訊息框改（或直接用預填的那句）→ 按下送出。
4. 成功顯示成功；失敗顯示**四種投遞失敗原因**之一。
5. 要拿掉時按移除 → **先確認** → 回到「還沒有設定」。

**Core Business Rules**

- **R1 — 這一頁需要登入。** 沿用既有的把關做法，被擋下的人登入後回到**這一頁**。
- **R2 — 密碼看不到是刻意的，要直說。** 不留白、不寫「無法取得」。
- **R3 — 「再打一次」是畫面自己的規則。**
  後端只收得到一組新密碼，看不出使用者第二次打錯，所以這一條只能由畫面守。
- **R4 — 後端的拒絕掛回出問題的那一格。**
  沿用登入畫面的既有做法：籠統的一句話等於要使用者自己猜是哪一格。
- **R5 — 換密碼成功要先說一聲再導走。**
  不說就把人踢回登入畫面，看起來像換失敗了——而他其實已經換好了。
- **R6 — 送出中按鈕停用。**
  換密碼特別要緊：第二次送出帶的是**已經失效的舊密碼**，
  使用者會看到「目前的密碼不正確」，但密碼其實已經換好了。
- **R7 — 金鑰那一格永遠是空的。**
  它拿不回來，留半串在畫面上只會讓人以為它還在。
- **R8 — 「還沒有設定」是空狀態，不是錯誤。** 連不上後端則是錯誤，兩者不能長得一樣。
- **R9 — 四種投遞失敗原因顯示四句不同的話**，且**靠後端回應帶了哪一種來分辨，不讀訊息文字**
  （沿用「三種算不出來」既有的做法：文字是寫給人看的，改一次措辭就會失效）。
- **R10 — 訊息長度畫面自己先擋**（空白、超過 4096 字元），超過時顯示目前字數。
- **R11 — 移除要先確認。**

**Edge Cases**

| 狀況 | 行為 |
| :--- | :--- |
| 換密碼的同時這一段登入剛好過期 | 沿用既有做法先把這一段救回來再重發；救不回來就帶回登入畫面 |
| 換密碼成功後，畫面上其他區塊還在讀資料 | 那些請求的結果一律丟棄，人已經要走了 |
| 使用者在測試訊息送出中換頁 | 不阻擋換頁；回來時那次送出的結果不再顯示 |
| 儲存 Telegram 設定成功、但接著送測試訊息失敗 | 設定仍然是已設定的樣子（後端不會因為送不出去而改動設定），只顯示那一次的失敗原因 |
| 三個區塊各自出錯 | 各說各的，一個區塊的錯誤不覆蓋另一個區塊 |
| 貼上超長訊息 | 不截斷輸入框內容，只是按鈕按不下去並顯示字數——截掉他貼的東西比擋下來更糟 |

## 5. UI/UX Design & Interaction

- **Prototype Link:** 無設計稿。沿用操作台既有的框架與元件語彙。
- **版面：** 設定畫面在既有樣板的工作區裡，是**一張置中的紙**（上限 47rem），
  紙上**四個段落**由髮絲線分開，不各自畫框——它們是同一頁的四段，不是四件不相干的事。
  每個段落左邊是標題與一句說明、右邊是可以動的東西（窄螢幕時上下疊）：
  1. **帳號** —— 電子郵件、遮住的密碼。
  2. **更換密碼** —— 三格 + 一顆「更換密碼」。
  3. **Telegram 投遞** —— 一行狀態（已設定／還沒有設定 + 金鑰結尾）、
     兩格 + 「儲存／更換設定」與安靜的「移除設定」。
  4. **試送一則訊息** —— 訊息輸入框 + 字數 + 「送出測試訊息」。
- **一頁只有一條右緣：** 四個段落的欄位與按鈕共用同一個寬度上限，切在同一條線上。
  各段自訂寬度的話，一頁會切出四條參差的邊。
- **一段只有一顆實心按鈕：** 「送出測試訊息」刻意是次要的——試送不改變任何東西，
  它是一次檢查，不是一個決定。
- **側欄：** `DESTINATIONS` 多一項「設定」，排在最後。
- **Key Interactions:**
  - 三顆送出鍵在進行中一律停用並顯示進行中。
  - 每一格的說明**就地顯示在那一格底下**，不集中在卡片頂端。
  - 「移除設定」是安靜的那一種（滑過去才紅），擺在動作列最左邊、與主要動作隔開；
    按下後跳一次確認，確認才真的移除。兩顆都畫成實心色塊的話，
    一整段裡最搶眼的會是那顆會弄丟東西的。
  - 測試訊息輸入框是多行，底下顯示目前字數與上限。
- **Empty state:** Telegram 區塊在還沒設定過時顯示「還沒有設定」與該填什麼，**不是錯誤樣式**。
- **Loading state:** 進入畫面讀取目前設定時，Telegram 區塊顯示讀取中，
  **不先顯示「還沒有設定」**——那會讓已經設定過的人以為設定不見了。
- **Error state:** 連不上後端時整頁明講，比照其他畫面。

## 6. Non-Functional Requirements

- **Performance:** 進入畫面只讀一次目前設定。三個區塊互不阻塞。
- **Security:**
  - **完整的機器人金鑰不留在畫面上**：儲存成功即清空那一格，也不寫進瀏覽器的任何儲存。
  - 密碼三格**不記住、不自動填、不寫進瀏覽器儲存**；離開這一頁即消失。
  - 換密碼成功後，本機記著的憑證一律清乾淨——後端那一側已經全部作廢，
    留著只會讓下一次請求拿一份必定被拒的東西去撞牆。
- **Compatibility:** 桌機瀏覽器；窄螢幕時三張卡片疊成一欄。
- **Analytics / Tracking:** 無。

## 7. Dependencies & Risks

- **External Dependencies:** 無（Telegram 由後端去打，前端只認識 go-trading）。
- **Internal Dependencies:**
  - 後端 `go-trading` 的 `2026-09-10-password-change` 與 `2026-09-10-telegram-delivery`
    兩個切片。**前端不能早於它們完成。**
  - `2026-09-05-user-sign-in`：把關、記住原本要去的地方、錯誤掛回那一格、連不上後端的呈現。
- **Known Risks:**
  - **後端的四種投遞失敗原因若不可分辨，US-05 就做不到。**
    這是前端對後端的硬性依賴，`architecture` 階段要先確認後端真的分得出來。
  - **換完密碼被帶回登入畫面**容易被誤讀成失敗。R5 是唯一的緩解，不能省。
  - 三個區塊擠在一頁，狀態彼此獨立卻長在同一個畫面上，
    很容易寫成「一個錯誤蓋掉全部」。R8 與 Edge Cases 最後一列是防這件事的。
